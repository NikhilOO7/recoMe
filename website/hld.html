01 Foundation

System Architecture Overview

RecoMe is a browser extension built on Chrome's Manifest V3 architecture. Think of it as three separate programs running at the same time, talking to each other through messages — like departments in a company communicating via internal memos.

📌 What

A multi-process browser extension with a content script (interacts with web pages), a background service worker (the brain), and UI panels (popup, DevTools). Each runs in its own isolated sandbox.

🌱 Why

Chrome enforces process isolation for security — a content script can't directly access IndexedDB, and the background can't touch the DOM. This separation is a security boundary that protects both the user and the extension.

⚙️ How

Each process communicates via chrome.runtime.sendMessage() — an async request/response pattern. The background service worker acts as a central router, dispatching messages to the right handler.

⏰ When

The content script loads on every HTTPS page (document_idle). The background starts when Chrome launches. The popup opens on icon click. DevTools opens from Chrome's developer panel.

High-Level Architecture — Process Model
Why three processes? Imagine a restaurant: the waiter (content script) takes orders from each table (web page), the kitchen (background) prepares everything using recipes and ingredients (intelligence + memory), and the manager's office (popup/DevTools) lets the owner see how things are going and change the menu. They all talk through order tickets (messages), not by shouting across the room.

02 Communication

Message Passing System

Since the three processes can't share memory, they communicate by sending typed messages. Think of it like a postal system — every letter has a type (what kind of request) and a payload (the data).

📌 What

An async request/response system where every message is a TypeScript union type with type and payload fields. A central dispatcher in the background routes each message to the right handler.

🌱 Why

Type-safe messaging prevents runtime errors. If you send a PROCESS_CONTENT message, TypeScript guarantees the payload contains the right fields. This is like having a form for every type of request — no ambiguity.

⚙️ How

The background's messageHandler.ts uses an exhaustive switch statement — meaning if you add a new message type but forget to handle it, TypeScript throws a compile error. This guarantees nothing falls through the cracks.

⏰ When

Messages fire on every significant event: a card is detected (content → background), user blocks a topic (popup → background), DevTools requests health data (devtools → background).

03 Detection

Content Detection Pipeline

How does RecoMe know there's a YouTube video or Amazon product on the page? It uses a MutationObserver to watch the DOM for changes, platform-specific adapters to identify content cards, and metadata extraction to understand what each card is about.

📌 What

A pipeline that watches for new DOM elements, identifies recommendation cards using CSS selectors, extracts metadata (title, topics, price), and sends it to the background for scoring.

🌱 Why

Modern websites load content dynamically — infinite scroll, AJAX updates, single-page navigation. We can't just scan the page once on load. The MutationObserver pattern lets us react to changes as they happen.

⚙️ How

1) Observer detects new nodes → 2) Adapter matches CSS selectors → 3) Extract metadata from DOM → 4) Deduplicate by content ID → 5) Send PROCESS_CONTENT message → 6) Apply action (hide/show/boost) to the element.

⏰ When

Continuously, while browsing. The observer fires on every DOM mutation. A debounce (200ms) batches rapid changes. Content is scored once and cached to avoid redundant work.

Content Detection — From Page Load to Card Hidden
Real-world analogy: Think of a mail sorting facility. Letters arrive constantly (DOM mutations). A scanner reads the address (adapter matches selectors). A worker opens and categorizes each letter (metadata extraction). Then it's routed to the right department (scoring engine). Finally, the decision is applied — deliver, discard, or flag.
04 Intelligence

Scoring Engine

The heart of RecoMe. Every piece of content gets a score from -1 (definitely hide) to +1 (definitely boost). The score is calculated by combining 5 independent factors, each looking at a different signal.

📌 What

A weighted multi-factor scoring engine that evaluates content using 5 independent scoring functions. Each factor returns a value between -1 and +1, and these are combined with configurable weights into a final score.

🌱 Why

A single signal (like "user blocked crypto") isn't enough. Content has nuance. By combining explicit preferences (blocks/likes), learned patterns (behavior), and knowledge relationships (graph), we get much more accurate decisions.

⚙️ How

Each factor runs independently and returns a contribution. The final score = weighted sum of all factors. Thresholds map the score to an action: hide (<-0.4), suppress (-0.4 to -0.1), show (-0.1 to 0.3), or boost (>0.3).

⏰ When

Every time a new content card is detected. Scoring is synchronous in the background thread and typically completes in <15ms. Results are cached per content ID.

Design insight: The weights are tuned so that explicit user preferences always win. If you block a topic, it gets hidden no matter what other factors say. This is the "user is always right" principle — the system learns, but the user has the final say.
05 Learning

Memory & Learning System

RecoMe doesn't just follow rules — it learns. Every interaction (block, like, dwell, click) creates a memory entry that influences future scoring. Memories decay over time, so the system adapts as your interests change.

📌 What

An IndexedDB-backed memory service that stores typed events (feedback, search, implicit signal, pattern). Each entry has a strength field that decays over time using an exponential half-life function.

🌱 Why

Human interests change. If you were into running shoes last month but switched to hiking boots, the old preference should fade. Exponential decay with a 30-day half-life means old memories become weaker, but strong signals (many interactions) persist longer.

⚙️ How

Strength formula: current = initial × 0.5^(daysSince/30). A memory starts at strength 1.0, drops to 0.5 after 30 days, 0.25 after 60 days, etc. The decay alarm runs every 15 minutes to update strengths and prune dead entries.

⏰ When

Writes: on every user feedback, search, or implicit signal. Reads: during scoring (topic affinity factor queries recent memories). Decay: every 15 minutes via Chrome alarm.

1

Event Happens

User blocks "crypto" on YouTube, or dwells 30 seconds on a product page, or clicks through to an article about cameras.

2

Memory Entry Created

A typed entry is written to IndexedDB with: type (feedback/search/implicit), topics, entities, platform, timestamp, and initial strength (1.0).

3

Pattern Detection

After 3+ similar events, a mid-term pattern card is created: "avoids clickbait", "prefers Sony", "researching headphones". These are stronger signals that persist longer.

4

Scoring Uses Memories

When new content is scored, the Topic Affinity factor queries recent memories matching the content's topics, sums their decayed strengths, and produces a signal.

5

Decay & Cleanup

Every 15 minutes, the decay alarm recomputes strengths and deletes entries below 0.01. This keeps the database lean and the system adaptive.

06 Knowledge

Knowledge Graph

The graph maps relationships between topics, brands, and categories. If you block "spam", the graph knows "phishing" is related — so it gets penalized too. This is how RecoMe understands that interests connect.

📌 What

An entity-relationship graph stored in IndexedDB. Entities are things (topics, brands, categories). Relations are connections between them with typed edges (related_to, part_of, competes_with) and weighted strengths.

🌱 Why

Real-world knowledge is connected. "Sony" relates to "headphones" relates to "audio" relates to "music". Without a graph, you'd need to manually specify every possible connection. The graph lets preferences propagate through relationships.

⚙️ How

Pre-seeded with ~100 common relationships on install. Grows as you browse — when two topics appear together in content, a relation is strengthened. The CrossPlatformLinker runs daily to find patterns across platforms.

⏰ When

Queried during scoring (Graph Relations factor). Updated when content is processed and entities co-occur. Strengthened daily by the CrossPlatformLinker alarm.

07 AI

AI Brain & Agent System

The Brain is RecoMe's central orchestrator — it receives high-level tasks and delegates them to 6 specialized agents. Think of it as a CEO who knows which department head to call for each problem.

📌 What

A task router + agent registry pattern. The Brain receives tasks (user chat, content scoring, insight detection), determines which agent(s) should handle it, dispatches in parallel when possible, and merges results.

🌱 Why

One monolithic AI handler would be too complex and slow. By splitting into specialized agents, each one is simple, testable, and can run independently. This is the microservices pattern applied to AI — but inside a browser extension.

⚙️ How

TaskRouter analyzes the task type → selects agents → ContextAssembler gathers relevant memory/graph data → agents execute with tools (ToolExecutor) → ResponseMerger combines results → FeedbackLoop records outcomes.

⏰ When

On user chat messages, scheduled insight checks (every 30 min), content scoring (Filter agent), and when the overlay triggers quick actions.

Brain Orchestrator — Task Routing to Agents

FILTER Filter Agent

The fastest agent. Scores content in <15ms using the 5-factor model. Runs on every detected card. No LLM needed — pure algorithmic scoring.

SCOUT Scout Agent

Discovers trends and emerging interests. Analyzes browsing patterns, detects research sessions, identifies preference drift. Runs during scheduled insight checks.

ADVISOR Advisor Agent

Explains decisions. "Why was this hidden?" → "Because you blocked 'crypto' and this card's primary topic is cryptocurrency." Uses the Explainer module.

SHOPPER Shopper Agent

Product specialist. Compares items across retailers, tracks prices, manages the watchlist. Uses the Commerce engine for price intelligence.

SOCIAL Social Agent

Manages preference packs — shareable preference profiles. Build a "Cinephile Pack", export it, share with friends. Handles pack import/export.

GUARDIAN Guardian Agent

Safety and privacy watchdog. Validates that no sensitive data leaks, enforces rate limits on LLM calls, blocks malicious content patterns.

08 Platforms

Platform Adapters

Every website structures its HTML differently. YouTube uses different CSS classes than Amazon. Adapters are the translation layer — they know how to find and extract content cards on each platform.

📌 What

A Strategy pattern. A BaseAdapter defines the interface (getCardSelector, extractMetadata, applyAction). Each platform extends it with platform-specific CSS selectors and extraction logic.

🌱 Why

Without adapters, you'd need one giant if/else chain checking every possible website. The adapter pattern lets each platform's logic be isolated, testable, and independently updatable. If YouTube changes their HTML, only YouTubeAdapter needs updating.

09 Resilience

Self-Healing Selectors

Websites change their HTML all the time. When YouTube renames a CSS class, RecoMe doesn't break — the self-healing selector system automatically discovers new patterns and adapts.

📌 What

Four components working together: SelectorDiscovery (finds new patterns), SelectorHealth (monitors success rates), PathPatternCache (caches discovered paths), and ContentSignatures (fingerprints content structure).

🌱 Why

Hard-coded selectors are brittle. When a platform deploys a UI update, the extension silently stops working. Self-healing selectors turn a breaking change into a self-correcting event.

⚙️ How

SelectorHealth tracks success/failure rates per selector. When a selector drops below 30% success, SelectorDiscovery runs — it walks the DOM tree looking for elements matching content signatures (structural fingerprints). Discovered selectors are cached in PathPatternCache.

⏰ When

SelectorHealth runs a check alarm every 60 minutes. Discovery triggers automatically when health degrades. The cache persists across sessions via chrome.storage.local.

Real-world analogy: Imagine a delivery driver who knows the route to your house. If the city renames the street, the driver doesn't give up — they look for landmarks (content signatures) they recognize, find the new route, and update their map (cache). Next delivery uses the new route automatically.
10 Intelligence

Platform Intelligence

Each platform has unique signals. YouTube has watch time. Amazon has purchase history. Twitter has engagement metrics. The Platform Intelligence system extracts platform-specific insights and feeds them into the scoring pipeline.

PlatformIntelligenceEngine

Central coordinator. Detects the current platform, loads the right intelligence module, and combines signals from multiple sources (page context, interest graph, external enrichment).

Per-Platform Modules

8 specialized modules (YouTube, Amazon, Twitter, Instagram, Facebook, LinkedIn, eBay, Walmart). Each extracts platform-specific signals — like YouTube's "Shorts" vs "Long-form" distinction.

OpportunityRanker

Takes raw insights and ranks them by relevance, novelty, and actionability. "You've looked at 12 laptops" ranks higher than "You clicked one link about cats".

InsightRenderer

Converts ranked opportunities into user-facing messages shown in the overlay or popup. Handles formatting, priority, and deduplication.

11 Interface

Floating Overlay & Smart Prompts

The overlay is a draggable AI assistant that lives on every web page — no need to open the popup. Smart prompts detect when you're dwelling on content and ask intelligent follow-up questions.

📌 What

A Shadow DOM-isolated React component injected into every page. It renders inside a shadow root so the page's CSS can't affect it (and vice versa). States: collapsed (pill), mini (preview), expanded (full chat).

🌱 Why

Shadow DOM is critical. Without it, the page's CSS could break the overlay, or the overlay's CSS could break the page. Shadow DOM creates a CSS boundary — like an iframe but lighter.

Smart Prompts flow: DwellTracker detects you've been on a product page for 30+ seconds → SmartPromptEngine evaluates trigger conditions → PromptFatigueManager checks you haven't been prompted recently → PromptRenderer shows a non-intrusive card: "You've been looking at OLED TVs. Want me to track prices?"

13 Import

Platform Importers

Cold start is the #1 killer of recommendation systems. RecoMe solves it by importing your existing preferences from 7 platforms — so it knows what you like from day one.

Import Manager

Coordinates imports across platforms. Handles progress tracking, error recovery, and deduplication. Uses two parsing strategies: DataTakeoutParser (Google/Facebook exports) and LiveScrapeParser (in-page extraction).

14 Social

Social & Preference Packs

Preference Packs are shareable, curated bundles of preferences. Create a "Film Buff" pack with your movie-related blocks and boosts, export it as a file, and share it with friends.

📌 What

PackBuilder creates packs from your preferences. PackStore persists them. PackRenderer shows them in the UI. PackImporter applies external packs to your profile.

🌱 Why

Configuration is hard. If a friend already curated the perfect "No Clickbait" setup, why repeat the work? Packs make preferences portable and social.

15 Data

Storage Architecture

RecoMe uses three storage layers, each optimized for different access patterns. Think of it like a filing system: a desk drawer (in-memory), a filing cabinet (IndexedDB), and a shared folder (chrome.storage).

Three-Tier Storage Architecture
Why three tiers? In-memory is fast but lost on restart — perfect for ephemeral debugging data. IndexedDB is persistent and supports complex queries — perfect for the learning system. Chrome Storage is accessible from content scripts and syncs across devices — perfect for user settings. Each tier serves a different need.
16 Cloud

Cloud & Sync Architecture

The optional cloud layer handles cross-device sync, user authentication, and billing. Built on Hono (lightweight Node.js framework) with Prisma ORM and PostgreSQL.

Sync Engine

Uses CRDT (Conflict-free Replicated Data Types) for merge-without-conflicts sync. Each device can edit preferences offline, and changes merge cleanly when back online.

End-to-End Encryption

EncryptionClient encrypts all data before it leaves the browser. The server stores encrypted blobs — it can never read your preferences. Keys derived from your password via PBKDF2.

Authentication

JWT-based auth with refresh tokens. TokenService manages lifecycle. No passwords stored server-side — only bcrypt hashes.

Billing (Stripe)

StripeService handles subscription management. UsageTracker monitors API calls for quota enforcement. Free tier has no cloud features — premium unlocks sync + priority support.

18 Security

Security & Privacy Model

RecoMe's core principle: your data never leaves your device unless you explicitly opt in. Zero servers. Zero analytics. Zero tracking. Here's how that's enforced architecturally.

1

Process Isolation

Chrome enforces that the content script, background, and popup run in separate processes. A compromised content script can't access IndexedDB directly.

2

Shadow DOM Isolation

The overlay renders in a Shadow DOM — the page's JavaScript can't access or manipulate RecoMe's UI, and RecoMe's CSS can't leak into the page.

3

Content Security Policy

The manifest's CSP restricts what the extension can load: no inline scripts, no external resources except the user's chosen AI API endpoint.

4

API Key Security

If the user adds an AI API key, it's stored in chrome.storage.local (encrypted by Chrome). Requests go directly from the browser to the AI provider. RecoMe never proxies or sees the traffic.

5

Guardian Agent

The Guardian agent validates all outbound data, enforces rate limits on LLM calls, and ensures no personally identifiable information leaks into prompts.

20 Decisions

Key Design Decisions

Every architecture involves tradeoffs. Here are the most important decisions made in RecoMe and why they were made.

DecisionChoice MadeAlternative ConsideredWhy This Way
Processing location100% localCloud AI processingPrivacy is the core value prop. Cloud adds latency, cost, and trust requirements.
Storage engineIndexedDBSQLite (via WASM)IndexedDB is native to browsers, requires no WASM overhead, and supports structured data with indexes.
UI frameworkReact 19Vanilla JS, SvelteReact's component model matches extension panels well. React 19's concurrent features help with large DevTools renders.
Message architectureExhaustive switchEventEmitter, pub/subTypeScript's exhaustive switch guarantees every message type is handled — compile-time safety over runtime flexibility.
Monitoring dataIn-memory ring bufferPersistent loggingMonitoring is ephemeral — it shouldn't grow storage indefinitely. Ring buffer bounds memory use to 500 events.

LLM integrationBYOK (Bring Your Own Key)Bundled API keyNo recurring API costs for us. User controls their data. Works with any provider (Claude, GPT, Gemini).

The meta-principle: Every decision in RecoMe optimizes for user trust. Local processing over cloud. User API keys over bundled. Transparent scoring over black-box AI. Self-healing over manual updates. When in doubt, choose the option that gives the user more control.
