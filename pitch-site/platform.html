API Reference

8 Agent-Powered Endpoints

Every endpoint is backed by a dedicated AI agent. The API is stateless from the developer's perspective; the intelligence lives inside the agent layer.

Method Endpoint Agent Description
GET /api/v2/taste/preferences ScoutAgent Read a user's preference categories and weighted interest nodes from their knowledge graph.
POST /api/v2/taste/signals IngestAgent Submit behavioral signals (views, purchases, completions) to update the user's preference graph in real time.
GET /api/v2/recommendations/content AdvisorAgent Get ranked content recommendations personalized to a user's current taste graph state.
GET /api/v2/recommendations/products ShopperAgent Get ranked product recommendations with purchase intent scoring and price-point matching.
POST /api/v2/identity/permissions IdentityAgent + GuardianAgent Create, update, or revoke consent grants. GuardianAgent enforces scope boundaries and audit logs every access.
GET /api/v2/social/similar-users CommunityAgent Find anonymized users with 60%+ taste overlap (Taste Twins) for collaborative filtering. Returns similarity scores, overlap categories, and twin count — never PII.
GET /api/v2/social/twin-recommendations CommunityAgent Get cross-platform recommendations sourced from Taste Twins — products, courses, posts, and videos that matched users discovered and engaged with highly.
GET /api/v2/analytics/audience IntelligenceAgent B2B audience analytics: aggregate preference profiles, adjacent interest clusters, and taste segment breakdowns for any product category.

OAuth 2.0 Scopes

Apps request only the scopes they need. Users approve each scope individually. GuardianAgent enforces scope boundaries at the API layer — no scope creep possible.

recome:preferences:read Read the user's preference categories, interest nodes, and weighted taste scores.
recome:preferences:write Update or extend the user's preference profile with new taste signals.
recome:graph:read Query the user's full knowledge graph — nodes, edges, and relationship weights.
recome:signals:write Submit behavioral signals (engagement, purchase, completion) to refine the user's graph.
recome:recommendations:read Retrieve personalized content and product recommendations powered by the user's graph.
recome:social:twins Access Taste Twin matching and cross-user recommendations. Returns anonymized similarity data and twin-sourced recommendations — never user identities.
recome:analytics:read B2B only. Access anonymized aggregate audience analytics for a specified product category.

The Moat Within the Moat

Taste Twin Network

When two users share 60%+ taste overlap across their preference graphs, they become Taste Twins. What one discovers, the other sees — across every platform, every product category, every app in the ecosystem. This is collaborative filtering rebuilt on top of a universal preference graph.

How It Works

1
Graph Similarity Detection

CommunityAgent continuously computes taste-overlap scores between anonymized preference graphs. When two users cross the 60% similarity threshold, they form a Taste Twin pair. Matching is weighted — deep preferences (high-confidence, long-held) count more than casual signals.

↓
2
Cross-Pollination Engine

When User A discovers a product, course, post, or video that scores highly against their graph, CommunityAgent checks: does this content also match User B's graph? If both the content-to-graph score and the twin-similarity score exceed thresholds, the recommendation propagates.

↓
3
Privacy-First Delivery

User B sees: "People with similar taste discovered this." They never see User A's identity, browsing history, or graph details. The recommendation travels through the graph layer — anonymized, aggregated, and consent-gated at every step.

↓
4
Feedback Loop Strengthens the Match

When User B engages with the recommendation, the twin-similarity score updates. Accurate matches strengthen the pair. Poor matches decay it. The network self-corrects over time.

Honest Assessment

Critical Risks

The Platform API is the highest-ceiling product in the portfolio — and the highest risk. These are the honest failure modes and the mitigations designed into the architecture from day one.

⚠
Network Effect Dependency

The Platform API is only valuable if users have rich, populated preference graphs. An empty graph is worthless to a third-party developer. This means the platform is dependent on prior adoption of the extension, the app, and the SDK — the consumer and B2B products that build the graph in the first place. Mitigation: Phase 1 is the extension and SDK. Platform API is a Phase 3+ play. The investor thesis is that Phases 1 and 2 build the graph, and Phase 3 monetizes it as infrastructure. The sequencing is intentional.

⚠
Regulatory Risk — GDPR Article 22

GDPR Article 22 restricts automated decision-making based on personal data. If third-party apps use the RecoMe preference graph to make legally significant decisions (credit, employment, insurance), RecoMe could be implicated as the data source. Mitigation: GuardianAgent and the explicit consent model were designed around GDPR compliance from day one. The terms of service for the Platform API prohibit use in regulated decision-making contexts. Scope boundaries enforce what data can flow where. This was an architecture decision, not a legal afterthought.

⚠
Big Tech Response

If Google ships a "preference graph as a service" product, it competes directly on the B2B analytics story. Google has the data, the distribution, and the developer ecosystem. Mitigation: The decentralized/federated model is structurally impossible for Google to replicate — their business model requires centralized data control. "Preference data lives on Google's servers" is the opposite of the RecoMe value proposition. Additionally, antitrust scrutiny of Google's data practices makes a new data product a legal risk for them. The window is 18–24 months. The goal is to build the network effect before that window closes.
