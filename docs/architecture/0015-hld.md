                 └──────────────┘         └──────────────┘         └──────────────┘

**Actors**

- **End user** (consumer) — captures, sees their graph, gets agent notifications, asks chat questions on demand
- **IaaS developer** — builds their own product on top of `/v1/*`
- **Ops / founder** — admin tools, billing, audit

**Third-party services Recome depends on**

- **Anthropic Claude** — synthesis (Sonnet) + tool-call routing (Haiku) for chat + Synthesist + Decision agents
- **OpenAI** — `text-embedding-3-small` for vectorising topics and entities (abstracted; swappable for Voyage AI)
- **Stripe** — consumer subscriptions, IaaS usage-based billing via Meters
- **Resend** — transactional email (verification, password reset, digests)
- **Cloudflare R2** — Takeout uploads, signed export downloads
- **BetterStack** — status page + uptime probes

Recome **does not** depend on any LLM model provider for the existence of the graph; the graph is durable in Neo4j. LLMs are used at the edges (chat synthesis, optional copy-polish on agent emissions). A Claude outage degrades chat and Synthesist; it does not affect Recall, Mind Map, or the IaaS API.

### 2.1 The five containers

| Container   | Tech                                             | Responsibility                                                                                                                                       | Stateless?        |
| ----------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| `web`       | Next 16 (App Router + RSC) on Vercel             | All UI — landing, signup, dashboard, /paste, /inbox, /mind (P2), /grow (P3)                                                                          | Yes               |
| `cloud`     | Hono + Prisma on Fly.io                          | All API: auth, sync, billing, intelligence, agents, IaaS `/v1`. Owns BullMQ workers in same process for now (carve-out when queue depth demands it). | Yes               |
| `extension` | TypeScript MV3 — Chrome / Firefox                | Browser-side passive capture. Posts signal batches to `cloud`. Local IDB for offline accumulation.                                                   | N/A (client)      |
| `docs`      | Next 16 MD-rendered (planned P2)                 | `docs.recome.app` — public OpenAPI docs for IaaS                                                                                                     | Yes               |
| `pwa`       | Same `web` container, installable + share-target | Mobile-first capture surface                                                                                                                         | Yes (it IS `web`) |

### 2.2 Why one cloud container, not microservices

[0006 §1](0006-system-architecture.md) covers this. Summary: until a specific scaling constraint forces a split (e.g. agent-runtime memory pressure on the request path), we run one Hono process per Fly machine. Splitting is reversible; gluing back is not.

The carve-out we will do first (P3) is **BullMQ workers as separate Fly machines** — they share the same image but boot with `--worker` flag and skip Hono. This means agent runs that take >2 seconds (Curator pulling RSS feeds) don't compete with the request path for event loop.

## 3. The four key data flows

Each flow is one user-visible behaviour, the components that participate, and their interaction order. Detailed sequence diagrams are in [0016 LLD §4](0016-lld.md).

### 3.1 Capture flow (extension/paste/PWA/IaaS → graph)

```
[user action]  →  [capture surface]  →  POST /signals  →  cloud
                                                            │
                                                            ├─ validate (Zod, shared schemas)
                                                            ├─ upsertUser (Neo4j)
                                                            ├─ upsertTopics + upsertEntities (Neo4j)
                                                            ├─ upsertPage (Neo4j)
                                                            ├─ embed topics + entities (OpenAI)
                                                            ├─ upsert embeddings (Qdrant per-user namespace)
                                                            ├─ recordSignal (Neo4j)
                                                            └─ fire signalIngestTrigger (event agents)
                                                                  │
                                                                  └─ RecallAgent.runOne()
                                                                       │
                                                                       └─ on hit → AgentEvent in inbox
```

**Latency budget:** 250ms p95 from request landing to response sent.
**Async path:** OpenAI embedding (200–400ms) is on the critical path today. Move to BullMQ worker before P3.

### 3.2 Retrieval flow (user → trail / mind map)

```
[user opens /dashboard?topic=X]
       │
       └─ GET /intelligence/trails/X
              │
              ├─ Neo4j: trail nodes, hops, platforms, time span
              ├─ Neo4j: related topics (RELATED_TO weight)
              ├─ Qdrant: semantic neighbors of X (optional, capped)
              └─ json envelope back to web
```

**Latency budget:** 400ms p95.
**Mind Map flow (P2):** same shape but returns the graph projection — nodes + edges + cluster IDs from Louvain — for a windowed time range.

### 3.3 Agent flow (active background work)

Two trigger modes. Both run through the same `AgentRunner` lifecycle:

```
[event trigger]   signalIngestTrigger.fireSync()
[scheduled]       BullMQ cron job (P2.5+)
       │
       ▼
  AgentRunner.runOne(agent, ctx)
       │
       ├─ agent.canRun(ctx)              ──── false → skip silently
       ├─ Guardian.check(agent, ctx)     ──── deny → record AgentRun(capped)
       │     │
       │     ├─ opt-in / pause            (AgentSubscription)
       │     ├─ per-agent throttle        (Recall ≤ 2/wk)
       │     ├─ daily cost cap            (sum AgentRun.costMicros)
       │     └─ quiet hours               (22:00–08:00 UTC v1)
       │
       ├─ agent.run(ctx) → result        ──── 'failed'   → AgentRun(failed)
       │                                 ──── 'skipped'  → AgentRun(skipped)
       │                                 ──── 'succeeded'→
       │                                          │
       │                                          ├─ AgentEventStore.insert (dedupe by key, 24h)
       │                                          ├─ Guardian.recordEmission (updates throttle)
       │                                          └─ AgentRun(succeeded, meta.eventId)
       ▼
[user inbox / digest / push]
```

This lifecycle is the load-bearing primitive of Phase 2. Every new agent plugs in here — see [0014 §3-§9](0014-unique-product-surfaces.md#2-f-401--mind-map) for which surfaces use it.

### 3.4 IaaS request flow (developer → /v1)

```
POST /v1/signals
Authorization: Bearer rk_live_…
X-User-Id: their-internal-user-42
       │
       ▼
  apiKeyMiddleware
       │
       ├─ ApiKeyService.resolveBearer()       ──── invalid → 401
       ├─ enforce X-User-Id format            ──── bad     → 400
       ├─ tenant.status === ACTIVE check     ──── no      → 401
       │
       ▼
  V1Controller.post('/signals')
       │
       ├─ Zod.signalBatchSchema validate
       ├─ usageTracker.getUsage(tenantId)
       ├─ planQuota(plan) ceiling check       ──── exceed → 429 with resetsAt
       │
       ├─ userId = composeTenantUserId(tenantId, externalUserId)   ◀─── isolation invariant
       │
       ├─ IntelligenceService.ingestion.ingest()  ◀─── SAME pipeline as consumer
       │
       └─ bumpUsage(tenantId, 'signalsIngested', N)
```

**Crucial invariant:** the IaaS path delegates to the same `IntelligenceService.ingestion.ingest()` the consumer path uses. There is exactly one ingestion pipeline. The IaaS surface is a tenant-scoped adapter around it, not a parallel implementation. See [0009 §6](0009-data-model.md#6-multi-tenant-isolation) for the userId composition invariant + test pinning.

## 4. Non-functional requirements

What "good" means quantitatively. Every NFR has either a measurement source or is honestly labeled aspirational.

| Concern                    | Target                                                                        | Measurement                                                               | Why this number                                                                     |
| -------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **Capture p95 latency**    | < 250ms                                                                       | Sentry / BetterStack                                                      | Synchronous to user paste action; > 500ms feels broken                              |
| **Retrieval p95 latency**  | < 400ms                                                                       | Sentry                                                                    | Dashboard pages render below this; above, feel sluggish                             |
| **IaaS `/v1/signals` p95** | < 250ms (batch of 10)                                                         | Sentry, per-route                                                         | Devs benchmark; high latency loses integration                                      |
| **Chat first-token**       | < 1.5s                                                                        | Sentry                                                                    | TTFB threshold for streaming UI feel                                                |
| **Availability**           | 99.5% / month consumer; 99.9% / month IaaS                                    | BetterStack uptime probes                                                 | Consumer can tolerate scheduled maintenance; IaaS contractually can't (P3 with SLA) |
| **Data durability**        | Postgres PITR 7d, Neo4j daily snapshot, Qdrant snapshot daily, weekly R2 dump | Restore drill quarterly                                                   | Untested backups don't count                                                        |
| **Embedding cost ceiling** | < $0.30/MAU/mo                                                                | OpenAI billing / active-users                                             | If above, embedding cache hit ratio is the lever                                    |
| **Agent cost ceiling**     | < $1.00/MAU/mo aggregate; per-agent caps in ADR-0012 §4                       | AgentRun.costMicros sum                                                   | Above $1, Guardian daily caps fire and ops budget reopens                           |
| **GDPR delete completion** | < 24h end-to-end                                                              | AuditLog entries                                                          | Regulatory baseline                                                                 |
| **Cross-tenant isolation** | Zero leaks ever                                                               | Tested at `composeTenantUserId` + manual audit on every PR touching graph | Hard requirement                                                                    |

The cost NFRs are the unusual ones. They're load-bearing for the business model — see [0011 cost & GTM](0011-cost-and-iaas-gtm.md). If embedding spend creeps to $1/MAU, the consumer subscription math collapses at $8/mo.

### 4.1 Scaling targets (P3)

- **Concurrent users:** 10K MAU consumer
- **Concurrent IaaS tenants:** 100 paying + 1000 free trial
- **Peak ingest rate:** 200 signals/second (burst), 50 sustained
- **Daily signals across all tenants:** 5M
- **Neo4j nodes / relations:** 50M / 200M

Above these targets we add: read replicas for Postgres (Neon native), Neo4j AuraDB Pro upgrade, Qdrant shard upgrade, separate BullMQ worker fleet.

## 5. Cross-cutting concerns

### 5.1 Authentication & authorization

Two completely separate identity systems:

1. **Consumer (JWT)** — email/password or OAuth (Google). Access token 15min, refresh 30d (rotating). [`cloud/src/auth/`](../../cloud/src/auth/).
2. **IaaS (API key)** — `rk_(live|test)_<28 base64 chars>`. SHA-256-hashed at rest; raw shown once at issuance. Bearer header. Tenant context resolved at middleware; every write/query is tenant-scoped via `composeTenantUserId`. [`cloud/src/iaas/`](../../cloud/src/iaas/).

Internal: admin role on JWT for `/admin/*` routes. Audit log for every admin action.

### 5.2 Privacy & data ownership

The architecture enforces user data ownership:

- **One delete endpoint covers everything.** `IntelligenceService.forgetUser(userId)` cascades Neo4j + Qdrant + agent events + audit log. Both consumer (`DELETE /intelligence/me`) and IaaS (`DELETE /v1/users/:externalUserId`) call it.
- **No cross-user training.** Graph and vectors stay per-user. No aggregate ML training on individual user data without explicit opt-in (and we currently do none).
- **Loud audit log.** F-408 surface — user-visible record of every signal, agent run, and access. [0014 §9](0014-unique-product-surfaces.md#9-f-408--the-audit-log-of-you).
- **Personality Mirror is opt-in.** Default off. Single-button wipe. [0012 §2.4](0012-active-agents-and-personality-mirror.md#24-mind-map--personality-mirror).
- **GuardianAgent enforces consent at runtime.** Not just policy; code-level enforcement on every agent run.

### 5.3 Observability

| Signal          | Tool                               | Notes                                                       |
| --------------- | ---------------------------------- | ----------------------------------------------------------- |
| Structured logs | Pino → Grafana Loki                | Already in code; logger redacts known PII patterns          |
| Errors          | Sentry                             | Backend + browser; source-map upload from Vercel + Fly      |
| Traces          | OpenTelemetry → Grafana Tempo      | P2 work — instrument capture flow first                     |
| Metrics         | OpenTelemetry → Mimir / Prometheus | Per-route RED metrics; per-tenant counters in `TenantUsage` |
| Uptime          | BetterStack                        | External probes; status page consumes them                  |
| Synthetic       | Checkly                            | One scripted journey: signup → paste → trail render         |

[0010 security-privacy-ops](0010-security-privacy-ops.md) has the SLO and on-call detail.

### 5.4 Configuration & secrets

- **Local dev:** `cloud/.env` (gitignored); `cloud/.env.example` is the schema reference. Zod-validated at boot in `cloud/src/config.ts`.
- **Production:** Fly.io secrets (one source of truth per env), Vercel env vars for web.
- **Schema:** every config value is a Zod field with default. Boot fails fast if `INTELLIGENCE_ENABLED=true` but `NEO4J_*` missing — operator sees the mistake at deploy, not first request.

### 5.5 Cost & quota

Cost is treated as a first-class architectural concern, not an afterthought:

- **Per-user daily LLM cost cap** in GuardianAgent (default $0.10).
- **Per-tenant monthly quota** for IaaS in `usageTracker.planQuota()`.
- **Embedding cache in Redis** (planned P2) — 30d TTL, lookup by `sha256(text)`.
- **Haiku for routing, Sonnet only for synthesis** — model split inside chat backend.
- **Per-agent throttles** — Recall ≤ 2/wk hard-cap regardless of new signals; Concierge 4×/day per trail.

If any of these are violated, we lose money per active user. The architecture makes them load-bearing constraints rather than monitoring concerns.

## 7. Quality attributes & architectural drivers

The decisions in this architecture trace back to four drivers, in priority order. When a decision conflicts with multiple drivers, the higher-priority one wins.

1. **User data ownership.** The user owns their graph; can see it, export it, delete it. This drives: opt-in agents, audit log as feature, single `forgetUser` cascade, no cross-user training.
2. **Cost predictability.** Per-user costs must stay below subscription revenue. This drives: hard daily caps, embedding cache plan, model routing (Haiku/Sonnet), per-agent throttles.
3. **Multi-surface capture.** Six capture surfaces feed one graph. This drives: shared `IntelligenceService.ingest()`, schema sharing between consumer and IaaS, the tenant-userId composition pattern.
4. **Honest about what we are.** No personality inference, no irreversible agent actions, no cross-tenant data leaks. This drives: GuardianAgent's binding constraints, anti-features list in [0014 §10](0014-unique-product-surfaces.md#10-anti-features).

## 8. Deployment topology

[0002 deployment notes](0002-deployment-notes.md) and [0006 §6](0006-system-architecture.md) cover this. Summary:

- **Regions:** single region (`iad` Fly.io US East) until v2. EU region (`lhr`) added when first EU enterprise IaaS customer asks for data residency.
- **Compute:** Fly.io for cloud (autoscale, scale-to-zero idle), Vercel for web (edge-deployed Next 16).
- **Datastores:** Neon serverless Postgres (branching for staging), Neo4j AuraDB managed, Qdrant Cloud managed, Upstash Redis managed.
- **Edge:** Cloudflare DNS + WAF + CDN in front of everything.
- **CI/CD:** GitHub Actions → ghcr → fly deploy. Vercel for `web` previews on every PR.

Backups: Postgres PITR 7d (Neon free, 30d paid), Neo4j daily snapshot via AuraDB plus weekly export to R2, Qdrant snapshot daily to R2, Postgres logical dump weekly to R2 for "Neon goes away" disaster.

## 10. Open architectural decisions

Decisions not yet made; each will become its own ADR when decided. Recording here so they don't get lost.

1. **Price-data vendor for Concierge (F-403).** Keepa vs RainforestAPI vs Amazon Affiliate API. Make-vs-buy is decided (buy); vendor is not. Blocks F-403 implementation. Target: P2 W17.
2. **Embedding cache backing store.** Redis (Upstash) is the obvious answer but TTL + invalidation strategy matters. Target: P2 W16 ahead of cost ceiling work.
3. **BullMQ worker carve-out timing.** Right now agents run in the request process. When queue depth >10K or agent-run wall-clock-time blocks Hono event loop, carve out. Target: P3.
4. **Per-tenant agent customization for IaaS.** Can a tenant configure their own Concierge thresholds for their users? Or is it the same defaults for everyone? Target: after first 10 paying IaaS tenants signal demand.
5. **Mind Map cluster algorithm.** Louvain (cheap, fast) vs Leiden (better quality). Default Louvain; revisit if cluster instability bothers users. Target: P2 W21.
6. **Conversation persistence for chat-on-demand.** Postgres rows in `Conversation` + `ConversationMessage`, but max history retention TBD. Target: P2 before /ask ships.
7. **Schema migration strategy.** Prisma `migrate dev` workflow replacing the legacy `db push` is a P0 hard requirement before any further schema change ships to prod. Target: P1 W7.
8. **EU region.** Single-region default `iad`. EU added when first EU enterprise IaaS customer asks. Target: triggered by demand.

Each of these blocks a specific milestone; they're listed against `0004` roadmap weeks where applicable.

## 11. What this design explicitly does NOT support

For protection against scope creep. If a proposed feature requires any of these, it requires a new ADR.

- **Multi-region replication.** Single region until #8 above resolves.
- **Real-time graph mutation push to clients.** All clients pull on demand or via background polling. Websocket / SSE for graph deltas is rejected complexity.
- **Cross-tenant graph queries.** The userId composition pattern is one-way. Cross-tenant analytics is an offline ETL job, not a runtime query.
- **Custom LLM fine-tuning per user.** We use off-the-shelf models. User-specific behaviour comes from the graph (signal-grounded prompts), not from model weights.
- **Synchronous LLM calls on the capture path.** Embeddings already pushed off; chat is on-demand only.
- **Always-on screen / audio capture.** Limitless tried; was acquired; functionality disabled Dec 2025 [ADR-0013 §1.1](0013-competitive-positioning.md#11-personal-memory-category-is-in-flux). Different value model from ours.
